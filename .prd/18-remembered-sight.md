## Measured facts (main 88eb5b0)

- The sight flood (0x109c12, `map/view.rs`) runs in mode Sight from the leader (`map/view.rs:389`) and adds light. Mode Sight also sets `CELL_VISIBLE` on each cell it reaches (`:309-311`). When the ambient light is below full daylight, light sources add light in a second flood (`:390-391`).
- A cell the sight flood never reached draws `NOT_VISIBLE`. A cell it reached but that has no light draws `DARK` (`map/view.rs:555-565`). Both look black on screen.
- While a light burns, the clock raises the ambient light to at least 4 (`actors/clock.rs:425-427`). So a view with a light source has no `DARK` cells. At night without one, most cells are `DARK` (S1: 37 of 121 lit in Original).
- The HD compositor receives a frame with a per-pixel source plane, not a tile list (`crates/u6-core/src/hd.rs:160`).

## Contract

- **What is remembered.** Each map-window cell that was in sight keeps its look from its last sight, with the game time of that sight: its ground, and its objects that do not move. Actors are never remembered, and neither are objects that move with an actor (`objects/moves.rs:29` `moves_with_actor`: parted objects, 0x1a9, the serpent). The look is drawn in dark grey, in the window and through the HD compositor.
- **Where it is kept.** `gfx::cache::SightMemory` (`gfx/cache.rs:183`), keyed by level and world cell packed in 32 bits (`cell_key`, `:245`). A cell stays remembered after it leaves the window and while the party is on another level. It shows again, in grey, when it is back in the window and out of sight. Without unit C3 it is never saved; with C3 (Saved with the game, below: planned until it ships) a Save writes it beside the savegame.
  - A cell is 16 bytes (`Remembered`, `:237`): the minute of its last sight, its first layer, and whether it has more. A cell with more layers keeps all of them in a side table (`stacks`).
  - The minute is kept as a `u32` (`minute32`, `:261`; `age`, `:267`). Its horizon, `u32::MAX`, falls in the calendar's year 8 876: 8 715 game years after the start of the owner's game, so the game's clock never gets there in play (`real_the_minute_horizon_is_thousands_of_game_years_after_the_start`). The time saturates at the horizon too (`a_sight_before_the_minute_horizon_ages_through_day_5`):
    - a sight five days or more before the horizon ages through day 5 as any;
    - a sight less than five days before it stops aging at the day it has at the horizon, so it never reaches day 5;
    - a sight at or past it (a calendar set there, an edited save) stays at day 0.
    Such sights go only at load state or by the cap.
  - Load state (0x105350, a restore) forgets it all: `RenderCache::forget_sight`, `gfx/cache.rs:120`, called first in `saveload::load_state` (`saveload/restore.rs`). It also drops the memoized window, whose key names copies by slot. With unit C3 (below) it then reads the memory saved with the save it loads, if there is one for that save.
  - The window reset 0x133a96 (death, arrest, the healer) keeps it. The reset window shows the remembered cells.
- **Fading by game days.** The age is the game time since the cell's last sight, on the original's calendar: 60 minutes, 24 hours, days 1..28, months 1..12 (`minutes`, `gfx/cache.rs:332`). d is the whole days of 1440 minutes (`fade_of`, `:340`).

  | d (whole days) | 0 | 1 | 2 | 3 | 4 | 5 and later |
  |---|---|---|---|---|---|---|
  | pixels shown | 100 % | 50 % | 25 % | 12.5 % | 6.25 % | none: black, forgotten |
  | of a fully opaque 16 × 16 tile | 256 | 128 | 64 | 32 | 16 | 0 |

  A lit cell in sight is seen again at every framed render (its look taken again), so it is day 0. An unlit cell in sight (0x1bc) is not seen: it keeps the age of its last lit sight.
- **The pattern.** A fixed 4 × 4 ordered (Bayer) matrix on the original's pixel grid (`BAYER`, `gfx/cache.rs:319`; `keeps`, `:326`). It is anchored to the world: a cell is 16 pixels, so the cell's own column and row stand for the world's. Day d keeps the pixels whose threshold is below 16 >> d. Each day's pixels are a subset of the day before's, and 50 % is a checkerboard.
  - The window render first draws the cell's own tile (0xff or 0x1bc, black), then the remembered layers, writing only the kept pixels (`draw_remembered` and `blit_memory`, `gfx/view.rs:156` and `:107`). The overlay OR pass (masktype bit 2) obeys the same mask.
  - The missiles' redraw (`blit_remembered`, `gfx/view.rs:175`, called from `combat/present.rs`) and the cached window path draw the same way. The window cache keys a remembered box by its fade too.
  - In HD, only the kept pixels carry `FLAG_MEMORY`. The left-out pixels name the cell's own black tile, so the pattern holds at the original's pixel grid.
- **Frozen at last sight.** The shore merge 0x152dac rewrites map records in place (`gfx/anim.rs:121`, the only writer of record pixels after the load). A remembered layer of a record in the merge set, or of any record already rewritten (version not 0), keeps a copy of the record's pixels from that sight (`Frozen`).
  - The copies are an append-only store (`freeze`, `gfx/cache.rs:508`): one per record and content (pixels and transparency, compared in full behind a hash). A new version whose content was held before takes the copy it took then.
  - For each setting of the animation flags (`seams::anim_mode`, which picks how each animdata slot runs), the store's size is a constant of the game data, not of play. A merged record's content is its load content with the masked pixels of the records its source water tiles draw now (`gfx/anim.rs:111-117`). Those records come from a finite frame set: each animdata frame is the animation counter `& and_mask`, a byte, shifted (`gfx/anim.rs:147-156`), so the frames repeat every 256 ticks. So no copy is ever freed: a slot names one content until load state, and the window cache keys a copy by its slot.
  - A copy's image id is `FROZEN_BASE` + slot, at version 0 (`gfx/cache.rs:283`). `FROZEN_BASE` is 2048, past every record.
  - At most `MAX_COPIES` copies (8 192, `:310`), about 0.6 KiB each with the index, 5.39 MB in all. When the store is full and a cell in sight needs a new copy, that cell is forgotten: it is black once out of sight. Its older look is not kept, because it is not the look of its last sight.
  - A layer with no copy is of a record outside the shore-merge set at version 0, which nothing rewrites after the load. The animation's frames repeat every 256 ticks, and a whole cycle of 256 ticks rewrites no record outside that set (`real_a_rewritten_record_outside_the_shore_set_keeps_its_look`, `gfx/view.rs:1814`). So no remembered layer of the shore-merge set, or of a record rewritten before its sight, draws its record live.
- **Bounds.**
  - At most `MAX_CELLS` cells at any time (229 376, seven eighths of 2^18, `gfx/cache.rs:294`). The cap below keeps at most `MAX_CELLS` − 1 before any insert. `layers` asserts it before each `put` in debug builds (`:633`).
  - The cap (`cap`, `:560`) acts after a render once the next render's cells (`BOXES`, 121 in Original and 777 in Wide, at most that many new) could pass `MAX_CELLS`. It forgets the oldest sights first, down to seven eighths (200 704). Among the sights of the cutoff's own minute, the lowest keys go first, so the cells kept do not depend on the table's order. A walk passes the cap only above 228 599 cells in Wide (229 255 in Original).
  - The table. It starts small and doubles as cells come. It can reach 2^19 buckets (11.0 MB of cells retained), also below the cap: a sweep or the cap leaves deleted entries, and those can force the 2^18 → 2^19 growth when an insert finds no room with 114 688 cells or more before it. It never grows past 2^19 buckets. A cap never shrinks it, and hashbrown (behind std's `HashMap`) rehashes in place, allocating nothing, while the cells after an insert are at most half a table's full capacity (seven eighths of its buckets). That is 229 376 for 2^19 buckets, and the build checks it with a const assert (`:303`), whose comment cites the rule in this toolchain's std (Rust 1.96.1, hashbrown 0.16.1, `src/raw/mod.rs:184-193` and `:2799`) and in hashbrown 0.17.1. `the_cells_table_rehashes_in_place_at_2_19_buckets` (`:1591`) is capacity-recovery coverage. It churns until the 2^19 table's deleted entries have taken its room and its capacity is back at 2^19's full 458 752 with a rise of more than a render's cells since the sample before. Since the cap never raises the capacity and every put is a new key, a render's inserts can take back at most that many deleted entries, so the larger rise needs a rehash. That the rehash is in place, allocating nothing, rests on the cited rule: the test sees the capacity, not allocations. In one run (std's `HashMap` is seeded anew each process), the first such rehash came after about 1.76 million cells put, 7.7 times the cap, in about 2.4 s, the capacity rising 240 844, in Original on this aarch64 machine, whose hashbrown control groups are 8 bytes (NEON, as on wasm32). Not run with 16-byte groups (SSE2), where deleted entries form far less often and the rehash may come past the test's limit: there the churn test does not assert the rehash, nor the bound test the stacks' table at 8 192 buckets or the 3 326 below (`EIGHT_BYTE_GROUPS`, `:1492`: true on aarch64 and wasm32, false on x86 and x86_64 and on the targets not considered). The test asserts the table never passes 2^19 buckets.
  - **Retained, not peak.** The figures below are what the memory retains (`heap_bytes`). The one growth to 2^19 buckets is the peak: for that moment the old table (2^18 buckets, 5.5 MB) and the new one (11.0 MB) live together, 16.5 MB of cell tables. Measured with a counting allocator (`crates/u6-core/tests/sight_memory_peak.rs`, the copies as in play), which runs only where the owner's zip is and prints `sight_memory_peak: ran` or `sight_memory_peak: skipped` (seen in a gate log with `--nocapture`): peak 16 824 576 bytes over the start in Wide and 17 249 040 in Original; then 11 352 800 and 11 732 364 retained. The test finds the growth by the 2^19 table's own allocation, allocated once and never a 2^20 one. The test runs on until 200 renders have passed and the cap has acted after the growth, and asserts both; in Original a render adds at most 121 new cells, so 200 renders alone may hold no cap. Only the cap lowers the cells held in the walk, and the test asserts each other way out: the sweep, since the teleport ticks the clock by 0 minutes (`map/travel.rs:93`), so no cell ages (the calendar is the same after every render); a fall in a render where the cap does not act, a load state's reset among them (every fall in the cells held lands on 200 704, where the cap always lands; a reset leaves at most a render's cells); and `forget` (a cell's look not kept), which needs a full copy store of 8 192 copies, about 5.4 MB, that the store, never freed, would still hold at the end (the heap retained at the end is at most the 2^19 table, the copies as in play and 1 MiB, 12 319 744 bytes [computed]). These asserts run with every width of control groups. With `U6_REQUIRE_ARCHIVE=1` a missing zip fails the test instead of skipping it. Not run with other widths than 8: there a walk that does not reach the growth, a cap and 200 renders past it before its grid ends waives the growth's and the peak's asserts but "never a 2^20 table"; one that reaches them asserts them all. It asserts that the high-water was set at the growth's render and passed by no later one (the cap's after it included), and that the peak is at least the two tables (16 515 072 bytes) and at most those, the copies and 1 MiB. With a full copy store the peak would be about 21.9 MB [computed]. The cap's scratch (`seen`, 917 504 bytes at the cap) lives at another moment. wasm32 linear memory keeps its high-water mark, so the page keeps the peak's pages.
  - **The retained ceiling, and its condition: a stack count.** With `MAX_COPIES` copies the memory retains under 16 MiB while there are at most 3 326 stacks [computed] (cells with more than one layer), about 1.45 % of the cap. That assumes each stack's layer vector has a capacity of 4, as two layers give it (the test's stacks); longer stacks retain more and lower the count. The 3 326 is exact for the test's state, with the latest index and the scratch empty. With the latest index and the scratch as play fills them, 0.1 to 0.9 KB more, the count is about 3 300 [computed].
    - The mechanism: the stacks' table (a stack's key and vector, 33 bytes a bucket) is at 4 096 buckets for up to 3 584 stacks. With 1 792 stacks or more before an insert, though, the deleted entries that `drop_stacks` leaves can use up the table's room, and that insert then grows it to 8 192 buckets (hashbrown's rule above), at 270 KB. After that step each stack costs 32 bytes of its vector, and the retained figure passes 16 MiB at 3 327 stacks [computed].
    - The cap's moment counts: right before each cap the memory holds the most cells and stacks of the cycle. The test takes the highest `heap_bytes()` over the whole run, after each render's puts and before its cap.
    - Measured (`the_bounds_hold_the_heap_under_16_mib`, `:1554`): the stacks are those at the run's high-water sample, not the most over the run. One cell in 100 stacked (`STACKED_LAND`, `:1474`) has 2 293 stacks at its high-water of 16 608 976 bytes in Original (2 287 and 16 608 784 in Wide). One cell in 70 (`STACKED_MOST`, `:1482`) has 3 275 stacks at 16 775 568 bytes, 1 648 bytes under 16 MiB (3 268 stacks, 16 775 344 bytes and 1 872 under in Wide). One cell in 67 has 3 422 at 16 780 272 bytes, 3 056 over. At one in 70 the test also asserts the stacks' table at 8 192 buckets and the ceiling's stack count, computed from the high-water sample (its bytes but 32 a stack, then 32 bytes a stack up to 16 MiB), as 3 326.
    - The land walks measured 0.51 % and 0.52 % stacked, the town walk 1.26 % (Cost below), about 2 890 stacks at the cap and 16 763 000 bytes [computed], under the ceiling but near it: a memory of denser towns alone could pass it.
  - Five game days of a Wide walk over unseen land hold at most 169 794 cells (with a light burning at night), 74 % of `MAX_CELLS`, and the cap forgot none over either run. That is a measured five-day count, not a bound. The walk's geometric bound is the start's view (777 cells) per start and teleport plus 37 cells a step (a new row of the Wide view): 777 × (1 + teleports) + 37 × steps, 357 864 and 368 816 for the two runs, above the cap. The receipt asserts the cells held stay within it after every step. A walk that shows more than the measured count (faster travel, a ship or the carpet, is not measured) passes the cap, and the oldest, most faded sights go first.
  - Cells of day 5 and later show nothing at once. A sweep forgets them (`sweep`, `:547`).
  - Four passes touch every cell: the sweep, at most once per game hour, and the cap, only when it acts (then not again for at least the next 27 896 new cells in Wide), both inside a framed render; hashbrown's in-place rehash, when deleted entries use up the table's room; and the table's growth, which moves every cell into the new table (at most once to 2^19 buckets after the doublings below it). Every other render touches only the cells of the view.
- **The grey.** One function serves classic and HD: `u6_render::grey` (`u6-render/src/lib.rs:125`), the luma `(77r + 150g + 29b + 128) >> 8` × `GREY_LEVEL` 115 / 256, rounded.
  - In classic, palette entries `GREY + i` (0x20..0x3f) hold the grey of game colour `i`, written by the map window render only while the switch is on. With the switch off, entries 32..63 are left alone, so the frames match the original pixel for pixel (visual parity, not 256-entry parity).
  - In HD, a pixel flagged `FLAG_MEMORY` (0x80) is drawn from the grey copy of its HD image.
- **HD pack art.** With an owner's HD pack loaded, the pack's picture is looked up by the record a copy came from (`Images::pack_id`, `u6-core/src/hd.rs:347`). It is shown only when the copy's own pixels hash to the pack picture's key (`HdPack::hd`, `u6-core/src/hd.rs:498`).
- **Darkness.** An unlit cell that is in sight (0x1bc) also shows its remembered look (`MEMORY_IN_DARKNESS`, one constant to veto it). Its age runs from its last lit sight. An all-dark window that is not a reset keeps the memory.
- **In sight is unchanged.** A cell in sight draws exactly as it did before, whether the switch is on or off (`real_a_cell_in_sight_is_the_same_with_the_switch_on_and_off`, both builds).
- **The switch.** `Io::set_sight_memory` defaults to off, so tests, oracle comparisons and receipts see the original's frames. The page turns it on for each game. A visitor who stores `localStorage['u6.memory'] = 'off'` keeps it off.

## Saved with the game (unit C3; shipped in deploy 38)

The owner's follow-up asks that terrain seen once stays remembered ("한번이라도 본 지형은 계속 기억"). Until C3 a reload forgot it all. From C3 on, a Save writes the memory beside the savegame as one port-only file, and load state reads it back with the save it belongs to.

- **The file.** `savegame/u6sight` (`SIGHT_FILE`, `saveload/mod.rs`). The original's save code names only `savegame/objlist`, the 69 `savegame/objblk??` and their `.tmp` copies (`saveload/mod.rs`; 0x10d4e8, 0x10d6ac and 0x10dfb4 in `objects/mod.rs`), so no original name matches it and the original ignores it. It sits under `savegame/` because every store and reader of the port handles exactly that directory. It has no dot (the native store's `.part` temporary name replaces an extension) and fits 8.3. The original's files stay byte-compatible: the port writes them as before, and a save the original wrote loads as before (no `u6sight`: an empty memory, as at a load state before C3). To play a port save in the original, copy its `savegame/objlist` and blocks to the PLAYER disk and leave `u6sight` out: the original never reads it, and it can be larger (up to 7 421 996 bytes) than a floppy holds.
- **The format** (version 1, little-endian, fixed widths; `gfx/cache/saved.rs`):
  - a header of 44 bytes: the magic `u6sight` and a zero byte, the version (u32, 1), the objlist's length (u32) and its FNV-1a 64 digest (u64), the game hour of the last sweep (u64; `u64::MAX` for none), then the counts of copies, cells and layers (u32 each);
  - each copy in slot order, 290 bytes: its record (u16), its 256 pixels, and its 256 transparency flags as 32 bytes of bits (pixel i is bit i mod 8 of byte i / 8);
  - each cell in increasing key order (`cell_key`), 10 bytes and 6 a layer: its key (u32), the minute of its last sight (u32), its layer count (u16, at least 1), then each layer's record (u16), masktype, overlay frame (a byte each) and copy slot (u16; 0xffff for none).
  - That is everything `SightMemory` needs for the same picture and the same fading: the cells, their minutes and layers, the copies the layers name by slot, and the hour of the last sweep. The rest is rebuilt empty or from these: the index of copies by content (from the copies, in slot order), the last-version index (keyed by record versions, which start again at 0 in a new engine), the scratch.
- **Bounds.** At most `MAX_COPIES` copies, `MAX_CELLS` cells and `MAX_SAVED_LAYERS` layers (2 × `MAX_CELLS`, 458 752): 44 + 290 × copies + 10 × cells + 6 × layers bytes, at most 7 421 996 (`MAX_SIGHT_FILE_BYTES`). A memory with more layers than that (no walk has come near: 876 of 169 762 cells stacked in five days of the Wide walk, Cost) is written without its oldest sights, in the cap's order (the oldest minute first; of one minute, the lowest keys first), until its layers fit. A cell of one layer is 16 bytes. The writer leaves out a cell the reader would refuse (a key out of range, a layer's record past the 2048 or its copy slot past the copies, an empty stack; none happens in play), so one such cell never costs the whole file.
  - **Saving and restoring it** (`a_save_and_a_restore_of_a_full_memory_hold_one_memory_and_one_file`, in the allocator-counting harness above, `crates/u6-core/tests/sight_memory_peak.rs`; native aarch64, gate profile; not measured in the page). A memory at the cap, its most cells after a render (229 255 in Original, 228 599 in Wide) of one layer each and a full copy store (8 192 copies), on the owner's game state, is saved twice and then restored. Each step's peak over the heap before it, in bytes:

    | build | the memory's own heap | its file | first Save | second Save | Restore | with nothing remembered: Save, Restore |
    |---|---|---|---|---|---|---|
    | Original, round 1 | 10 895 376 | 6 043 804 | 15 356 715 | 15 356 715 | 10 910 857 | 25 570, 26 303 |
    | Original | 10 895 376 | 6 043 804 | 6 968 107 | 924 263 | 26 303 | 25 570, 26 303 |
    | Wide, round 1 | 10 895 376 | 6 033 308 | 15 343 595 | 15 343 595 | 10 910 857 | 25 710, 26 331 |
    | Wide | 10 895 376 | 6 033 308 | 6 954 987 | 921 639 | 26 331 | 25 710, 26 331 |

    - A Save drops the last Save's file first (`SaveLoad::sight` = none), then writes the cells straight from the memory, in key order, into one buffer of the file's size, which it keeps as the file (`SavedSight` holds that buffer, no copy). Besides the file it allocates the sorted keys, 4 bytes a cell (917 020 bytes at the cap in Original). Past `MAX_SAVED_LAYERS` (never in play) it sorts the cells by sight too: a tuple of 16 bytes a cell more (12 on wasm32), in a vector grown by doubling. So a second Save peaks at the keys and the Save's own work, not at a second file.
    - A Restore forgets the memory (`forget_sight`) before it reads the file's, so the two never live together: it peaks at its own work, as with nothing remembered, when the memory it reads is no larger than the one it forgot.
    - Round 1's Save held the file, the sorted keys and every kept cell as a 32-byte tuple together, in a vector grown by doubling (at the cap 917 020 bytes of keys, 8 388 608 of tuples and the file's 6 043 804: with its own work, its peak), then copied the file into a shared slice; a second Save did the same with the last file still held, each Save's peak the same. Its Restore read the new memory while the old one lived (10 910 857 over the heap before it: a second memory).
    - The bound the test asserts, over the heap before each step: a Save at most the file, 4 bytes a cell and 64 KiB; a second Save at most 4 bytes a cell and 64 KiB; a Restore at most 64 KiB. Round 1's figures fail all three.
    - What stays. Two copies of a file are kept: the platform's `savegame/u6sight` in the game files' save layer for the session (`attach`), and the last Save's (`SaveLoad::sight`): up to 12 MB together at the cap with a full copy store, 7.5 MB with the owner's 255 copies. And the store paths copy it while they run: `changed_since` (`saveload/store.rs`) and the page's whole-save list (`whole_save`, u6-web `lib.rs`) copy it into the list they hand over (`to_vec`); the page holds that list (`Game::save_out`) until the store reports the commit (`save_committed`); `MemStore::load` clones the stored files at `attach`.
- **The binding to its save.** The file holds the length and the FNV-1a 64 digest of the `savegame/objlist` bytes the Save wrote with it. Load state reads it only when the objlist it has just read has that length and digest. So a later save the original wrote over a port save, an imported folder from another game, and the new game of the character `u`, all start with an empty memory, not another game's. A collision of two different objlists of one length needs a 64-bit coincidence; two objlists of one length that differ in one byte never collide (FNV-1a's step is a bijection of the hash).
- **Malformed or unknown → ignored.** A file shorter than its header, of another magic or version, of another objlist, with a count past its bound, fewer layers than cells or a length not exactly the counts', a copy or layer record past the 2048 records, a copy slot past the copies, a layer count of 0 or a sum of layer counts other than the header's, a key not above the one before or out of range (a level past 5, or x or y past its level's mask: 0x3ff on the surface, 0xff below), is ignored whole: the memory stays empty, nothing panics, and nothing else of the load changes.
- **When it is written.** Only at a Save (0x105716, `saveload::save`), from the memory as the last render left it, with the objlist that Save writes, and only when the memory holds a cell. The switch (`Io::set_sight_memory`) stops new sights from being remembered and drawn; it does not drop a memory the save already holds: a game booted with the switch off keeps the memory it read, and its Save writes that memory again, bound to the objlist that Save writes. With the switch off from a fresh start (nothing ever remembered), or before anything was seen, a Save writes the original's files alone. Nothing is written while playing. The session keeps the file as the last Save wrote it (`SaveLoad::sight`, none when that Save wrote none) and the generation of that Save (`SaveLoad::sight_gen`). The save state's equality leaves the file out (`SaveLoad`'s `PartialEq`), as the game state's leaves the memory out.
- **The character `u`** writes a new game's `savegame/objlist` and a new save generation (`intro::handoff::apply`), and no `u6sight`. A `u6sight` stored from an earlier save stays in the store, and the session's last Save's stays in `SaveLoad::sight`, both harmless: their digest is of the earlier objlist, so a Restore, a relaunch and a reload all start the new game with an empty memory.
- **The trace.**
  1. Save: `save` writes back the region, encodes `objlist`, drops the last Save's file, then encodes the memory against those bytes (`RenderCache::sight_file`) into `SaveLoad::sight`, `sight_gen` = the Save's generation.
  2. The platform after the tick: `changed_since` lists `savegame/objlist`, the replaced blocks and, when `sight_gen` is past the generation stored, `savegame/u6sight` (so `u`'s generation does not list it again); `SaveSync::flush` (native, tests) and the page's `save_collect` hand them to the store. After the page removed the stored save, its whole-save list holds it too.
  3. The stores keep it as any save file: `MemStore`; native `DirStore` (`DIR/savegame/u6sight`, written as `u6sight.part` and renamed); the page's IndexedDB record `save:savegame/u6sight` in the Save's one transaction.
  4. The boot: `attach` lays it over the game files with the save (its filter `is_save_file` admits it). The page takes it from its store or from a dropped `savegame/` folder (`load_save`, `readSaves`) up to `MAX_SIGHT_FILE_BYTES`, its own limit beside the block files', and does not count it in the save's total (`MAX_SAVE_BYTES`, the original's files); a later copy of it within that limit, in another case of its name, replaces the one taken before (`Game::load_save`), and one past it is left out and replaces none. So of a drop's copies (in any folder, in any case of the name) the engine keeps the last within the limit, and the page reads that one alone, before reading any; the others are not read. The page's note names each file it left out with the limit that left it out (the file's own, or the save's total).
  5. Load state at the boot (`game_main`, before `finish_load_state`): the objlist it reads is the session's when it wrote one (`u`'s, or the last Save's before a relaunch), else the files'; the file it reads goes with it (`saved_sight`): the session's last Save's (none, or after `u` one of another objlist), else the files' `savegame/u6sight`. Decoded and checked against that objlist, it becomes the memory. Restore (0x1052c8 → 0x105350): `read_state_files` reads the objlist (the last Save's of this session, else the platform's) before anything changes; `load_state` forgets the memory (`forget_sight`, the window memo with it), then reads and checks the file that goes with that objlist, chosen the same way, and sets it. So the old memory goes before the new one is made (Bounds), and with no file, or one it refuses, the memory stays forgotten, as before C3.
  6. The read keeps the reading build's cap: a file written in Original (121 cells a render) read in Wide (777) is capped at once if its cells and a render's could pass `MAX_CELLS`.
- **Days across the reload.** A cell keeps the minute of its last sight on the calendar (`minutes`), and load state reads the calendar the save holds. So a reload is not a new day: the fade goes on by game days from the saved clock, the same with or without the reload. A sight at or past the calendar read (an edited calendar) stays at day 0, as above.
